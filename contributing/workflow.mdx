All day-to-day contributor work goes through a single entry-point script, `decomp.py`. You should not need to call the internal tools directly — the wrapper handles dispatching into the container, refreshing the report, and running promotion automatically. The sections below walk through every action you will take on a typical contribution day.

## Working on a unit

To rebuild a unit and see its per-function match table, pass the source path to `decomp.py`:

```bash
python decomp.py src/game/creature.c
```

This rebuilds the unit, refreshes the report, and prints a table like the following:

```text
Unit: game/creature
Compiler: default

Function                  Match      State         Verified
----------------------------------------------------------------
CreatureInit              100.00%    matching      yes
CreatureUpdate             96.42%    asm           no
CreatureDraw               73.18%    asm           no

Unit fuzzy progress:       89.31%
Verified matching:          1 / 3
```

### Understanding the three columns

The three columns carry different kinds of authority and must not be conflated.

<CardGroup cols={3}>
  <Card title="Match" icon="percent">
    The **objdiff fuzzy percentage** — the same score CI and decomp.dev display. It is a useful guide for how close a function is, but it is not proof of correctness. A function can read 100% and still fail the byte gate.
  </Card>
  <Card title="State" icon="tag">
    The **committed manifest state** — one of `asm`, `equivalent`, or `matching`. This is what the status manifest on disk actually says, and it is what determines how the hybrid object is built.
  </Card>
  <Card title="Verified" icon="shield-check">
    The **canonical truth** — `yes` means the bytes were re-derived and proven identical to the retail ELF by `tools/promote.py`. This is the only measure that matters for the byte gate.
  </Card>
</CardGroup>

## State lifecycle

Every function in a unit begins its life in `asm` state — the assembler slice from the retail binary stands in for the C. From there, two paths exist:

<Steps>
  <Step title="asm">
    The initial state. The function's retail assembly slice is used in the hybrid object. The `decomp.py` table shows `State: asm` and `Verified: no`.
  </Step>
  <Step title="equivalent (human review)">
    A reviewer has examined the C and the retail assembly and judged them semantically equivalent — the behaviour matches even if the bytes do not. This state is **always a human decision** and is **never set automatically**. Edit the manifest field directly to record this judgment.
  </Step>
  <Step title="matching (byte-verified)">
    The function's compiled output is byte-identical to the retail slice over its full registry extent, and the full loaded image reproduces the retail SHA-256. This state is **only ever written by `tools/promote.py`** after passing every gate. It is never set by hand.
  </Step>
</Steps>

<Warning>
  **Never hand-edit a manifest to `state = "matching"`**. Only `tools/promote.py` writes that value, and only after byte verification. A manually promoted function will pass `status.py --check` in the short term but will produce a corrupted hybrid and fail `verify-promoted` in CI.
</Warning>

## Auto-promotion

Any function whose `Match` column reaches **100%** while still in `asm` state is automatically promoted by the wrapper. Under the hood, `decomp.py` calls `tools/promote.py`, which:

1. Compiles the function with the unit's locked profile compiler.
2. Re-derives the bytes over the function's full registry extent.
3. Re-links the full loaded image and checks the retail SHA-256 (`c92a59870d47441bbd3f741eca2be42ccbbab28b7d0670d96e09c2f2340fe438`).
4. Writes `state = "matching"` to the manifest **only if all three gates pass**, or rolls the manifest back to `asm` otherwise.

If you want to inspect the table after a rebuild without triggering promotion, pass `--no-promote`:

```bash
python decomp.py src/game/creature.c --no-promote
```

## Creating an initial manifest

If a unit has no status manifest yet, `promote.py --init` scaffolds one with every function in `asm` state. Without this file, `decomp.py` will error out when it tries to read the manifest.

```bash
python tools/promote.py --init src/<group>/<unit>.c
```

Replace `<group>/<unit>` with the path relative to `src/` — for example, `src/nucore/nulist.c` produces a manifest at `config/pal103/status/nucore/nulist.toml`.

<Note>
  After adding a new source file or manifest, regenerate the build graph so ninja picks up the new edges: run `python tools/gen_ninja.py` (or `python configure.py`, which also regenerates it).
</Note>
