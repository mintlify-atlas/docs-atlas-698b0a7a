With the loaded image reconstructible from per-TU assembly objects, decompilation proper begins: replacing each translation unit's assembly with hand-written C that compiles to the exact retail bytes. This is the ongoing work of the project — every function starts in assembly and is promoted to C only after byte-exact verification through a controlled pipeline that prevents any unverified claim from influencing the image gate.

## Unit Structure and Function States

Each translation unit `nucore/nulist` decompiles into `src/nucore/nulist.c` — clean C, no `INCLUDE_ASM` annotations — with a status manifest at `config/pal103/status/nucore/nulist.toml` that marks every function with one of three states:

| State | Meaning |
|---|---|
| `asm` | unmatched; the retail assembly object is used in the linked image |
| `equivalent` | reviewed as semantically equivalent, but not byte-exact |
| `matching` | byte-proven identical to retail; only `tools/promote.py` may write this |

## Hybrid Objects

`tools/gen_hybrid.py` compiles a unit with its compiler profile (`ee-gcc -S`), then splices — in retail address order — the compiled C for each `matching` or `equivalent` function and the retail assembly slice for every other function. It normalizes the two compilers' differing pseudo-op encodings and assembles the result with the decompals `as`.

Two link sets are produced from each hybrid:

- **`matching`** — byte-exact C for proven functions, retail assembly slices for everything else. This set must reproduce the retail bytes exactly and feeds the image gate.
- **`equivalent`** — reviewed-equivalent C compiles in too. This set only has to link — it is the modding build, and may diverge from retail bytes.

## The Build Graph

`build.ninja` (generated by `tools/gen_ninja.py`) builds four object sets per unit:

| Set | What it is |
|---|---|
| `current` | plain compile of the C — the honest objdiff score |
| `report-current` | C with hybrid normalization — used as objdiff's base so a verified `matching` function reads 100% (the raw `current` object misses by `.lit4` pool placement) |
| `matching` | byte-exact hybrid — links the full image for the byte gate |
| `equivalent` | modding hybrid — must link, may diverge |

The `current` set gives an unmodified view of how close the C is to retail; `report-current` is the normalized form used in the published objdiff report so that a byte-verified function scores exactly 100% rather than drifting due to assembler pool differences.

## Canonical Verification with promote.py

Byte verification is centralized and non-bypassable. `tools/promote.py` is the **only** writer of `state = "matching"` in any manifest. When invoked, it re-derives every `matching` claim byte-for-byte over the function's full registry extent, then ends in `tools/link_image.py` relinking the whole image and checking the retail SHA-256:

```text
c92a59870d47441bbd3f741eca2be42ccbbab28b7d0670d96e09c2f2340fe438
```

The public objdiff report is a *measurement* layered on top of this gate — it can never move a byte gate or grant a function `matching` status. A function either passes `promote.py`'s byte check, or it stays `asm` or `equivalent`.

## First Matched Unit

The first matched unit is `src/nucore/nulist.c`. `NuListGetHead` and `NuListGetTail` are byte-identical to the retail build. Not every runtime function is C — `strlen`, for example, is hand-written R5900 SIMD assembly in the retail build and stays as `asm`.

## Checking a Promotion

To promote a function to `matching`, run `promote.py` against the unit's source file. It handles the full verification chain:

```bash
python tools/promote.py src/nucore/nulist.c
```

`tools/verify_promoted.py` re-derives every existing `matching` claim in CI, ensuring no previously-verified function regresses between commits.

<Warning>
  Never hand-edit a manifest to set `state = "matching"`. Only `tools/promote.py` writes that state, after completing the full byte-verification chain through `tools/link_image.py`. A hand-edited manifest will be caught and rejected by `verify_promoted.py` in CI.
</Warning>

<Note>
  This step requires both toolchains at once — the EE GCC compiler and the PS2 binutils — so it runs inside the Containerfile image, which pairs Debian trixie's glibc (for the binutils) with i386 multilib (for the 32-bit compiler). The C in `src/` is the committed work product; every generated artifact is game-derived and gitignored: object sets in `build/`, expected objects in `expected/`, and `objdiff.json`.
</Note>
